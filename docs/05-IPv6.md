# Add IPv6: the endpoint first, then addresses inside the VPN

Add IPv6 after the IPv4 tunnel and internet access work. At each step, test the client's path to the server separately from the traffic carried inside the tunnel. A working connection to an IPv6 server does not by itself give clients working IPv6 internet access.

## 1. Decide what IPv6 will carry

A client can connect WireGuard/OpenVPN to an IPv6 endpoint while carrying only IPv4 inside the tunnel. It can also carry IPv6 payload over an IPv4 transport. An IKEv2 handshake alone does not prove that the client has usable public IPv6. Record both the outer transport and the inner traffic for every measurement.

For the WireGuard endpoint, use an AAAA record for a server that is reachable over IPv6, or an address such as `[2001:db8:100::10]:51820` in the client profile. The server must accept UDP on that address, and both firewalls must allow the port. First check for a new handshake and verify that the existing IPv4 traffic still works. This change does not require changing the addresses inside the tunnel.

For OpenVPN, replace `proto udp4` with `proto udp6` in the matching UDP server and client profiles. The TCP version uses `tcp6-server` and `tcp6-client`. This selects the outer transport; it does not assign IPv6 addresses to clients. Do not create a second process using the same pool and virtual adapter. OpenVPN 2.7 supports multiple `local host port protocol` directives for listeners using both IP families. Check the specific bind and DCO combination against the manual, logs and actual sockets. [OpenVPN 2.7 manual](https://openvpn.net/community-docs/community-articles/openvpn-2-7-manual/).

To provide public IPv6 inside the tunnel, you need:

1. An allocated prefix and permission from the provider to use it for VPN clients.
2. Outbound routing/forwarding on the server and a return route on the provider's router.
3. Correct addresses and client routes, including an exact `/128` in the server's AllowedIPs for each WG client.
4. The required ICMPv6 traffic, including Packet Too Big, and working PMTUD. Do not block ICMPv6 as a whole.
5. Firewall rules for client traffic and access to the server. A public client address does not mean its services should be open to everyone.

The documentation prefix `2001:db8::/32` must not be used on the public internet. Replace the addresses below with addresses actually allocated to you. IPv6 payload is not translated through IPv4 WinNAT in this setup.

## 2. Obtain prefixes routed by the provider

The provider routes dedicated VPN prefixes to the server, its WAN address or the relevant link. NDP on the WAN resolves the server, rather than each remote VPN client.

A prefix identifies an entire address range. Here, `/64` defines a network, while `/128` identifies one IPv6 address. When dividing the range, both the address and the prefix length matter. For example:

| Purpose | Example prefix | Procedure status |
| --- | --- | --- |
| WAN link | `2001:db8:100::/64` | the provider's own link |
| WireGuard | `2001:db8:200:1::/64` | routed design |
| OpenVPN UDP | `2001:db8:200:2::/64` | routed design |
| OpenVPN TCP | `2001:db8:200:3::/64` | routed design |
| RRAS/IKEv2 | `2001:db8:200:4::/64` | design requiring separate validation |

Every row uses a different `/64`. Prefixes such as `2001:db8:100:0:100::/64` and `2001:db8:100:0:101::/64` would normalize to **the same network**, `2001:db8:100::/64`. Changing the fifth group does not create separate networks when the prefix length is `/64`.

Before changing the VPN configurations, ask the provider to confirm the exact prefixes and their return route to your server. Being able to add an address in Windows does not create that route. When the provider routes the prefix to the server, it does not need to resolve each VPN client as a neighbor on the WAN.

## 3. Add WireGuard and OpenVPN addresses

The WireGuard server can use `2001:db8:200:1::1/64`, with a peer using an address such as `2001:db8:200:1::2/128`. Add that exact `/128` alongside the IPv4 `/32` in the server's peer section. On the client, add its IPv6 address to `Address` and, for a full tunnel, add `::/0` to `AllowedIPs`. Check the upstream route and the local route through the WG interface.

The matching templates are `config/wireguard-server-dualstack.conf.example` and `config/wireguard-client-dualstack.conf.example`. They contain no real keys and do not allocate the documentation prefix for production use. The generator in the main guide creates only the initial IPv4 version. Enable dual stack manually after confirming the prefix allocation and routing.

For OpenVPN, add an overlay such as the following to the matching server profile. It does not change the outer `udp4`/`udp6` listener:

```text
server-ipv6 2001:db8:200:2::/64
push "route-ipv6 2000::/3"
```

Use a different allocated prefix for TCP. The `2000::/3` route covers public global unicast addresses. It is not a complete IPv6 default route or a kill switch. Define and test the client policy for all IPv6 destinations and leaks, including DNS, according to your full tunnel requirements. Check dynamic assignments in the status file and on the client; do not guess where the pool starts.

The supplied `openvpn-udp-ipv6-payload.overlay.example` and `openvpn-tcp-ipv6-payload.overlay.example` files contain only additions for the payload configuration. Replace the prefixes and merge them into the correct server profile. **Do not save an overlay on its own as another .ovpn file in config-auto.** The client profile using `client` accepts address assignments and pushed routes from the server. Then check the actual IPv6 address and routes on the client, because platforms may handle some pushed options differently.

After a planned restart of the affected service, both the server and client should show addresses from your allocated prefixes. For WireGuard, also check the correct `/128` for each peer. For OpenVPN, compare the client's assignment with the status file. If the client has not received an address, resolve that before investigating internet routing.

## 4. Enable forwarding and check the return path

After adding the addresses and provider routes, enable IPv6 forwarding on the WAN and the actual tunnel interfaces. For WG/OVPN, you can deliberately set `EnableIPv6Forwarding` to `true` in the protected runtime copy of the routing JSON and run the initializer. It finds interfaces using the IPv4 addresses in the configuration. Editing the file in this package does not update the copy stored under ProgramData. Also check that the IPv6 default route remains available, because forwarding and Router Discovery can affect it. Do not change the default route or Router Discovery remotely without console access.

After backing up and editing the runtime JSON, display the plan before applying it:

```powershell
$routing = Join-Path $env:ProgramData 'WindowsVPN\Routing'
& (Join-Path $routing 'Initialize-VpnRouting.ps1') -ConfigPath (Join-Path $routing 'network.json')
& (Join-Path $routing 'Initialize-VpnRouting.ps1') -ConfigPath (Join-Path $routing 'network.json') -Apply -WhatIf
& (Join-Path $routing 'Initialize-VpnRouting.ps1') -ConfigPath (Join-Path $routing 'network.json') -Apply
Get-NetIPInterface -AddressFamily IPv6 | Select-Object InterfaceAlias,Forwarding,ConnectionState
Get-NetRoute -AddressFamily IPv6
```

Expect forwarding on the WAN and the tunnel interfaces in use, a working default route and routes to the client prefixes. Test client -> server, server -> client, and client -> an approved external IPv6 TCP destination. Then add DNS AAAA tests and a larger transfer. If only replies from the internet fail, focus on the return route, firewall and WAN neighbor resolution. Required ICMPv6 traffic, including Packet Too Big, must pass. [RFC 4861](https://www.rfc-editor.org/rfc/rfc4861).

## 5. Validate public IPv6 for IKEv2 separately

This package does not provide a verified installation procedure for public IPv6 with RRAS/IKEv2. This section defines the conditions for your own pilot test; it does not guarantee that the setup will work. Obtain a separate, routed `/64`, such as `2001:db8:200:4::/64`. A delegated `/56` is not required for one such network.

In the RRAS IPv6 properties, configure the approved IPv6 addresses/prefixes for your RRAS version and client type. Check which prefixes and addresses the system actually assigns. Do not copy a `/112` from OpenVPN into RRAS or treat that option as tested. The settings must match IPv6CP, RRAS and the specific clients.

Enable forwarding on the WAN and the current RRAS Internal interface. Provide a local route for the assigned client addresses and a provider route for the entire dedicated prefix to the server. Test client -> server, server -> client, client -> external IPv6 TCP and the reply, DNS AAAA, ICMPv6 Packet Too Big, and a restart. Mark this part as unverified until all steps pass. Working IPv4 RRAS NAT or a tunnel ULA does not replace these tests.

## 6. Consider the NDP helper only for an allocated on-link /64

Use this option only if the provider **has allocated the entire on-link `/64`** to this server/customer, permits additional addresses, and cannot provide a routed prefix. Seeing a `/64` on the server's network adapter does not prove that the entire range belongs to you. On a shared segment, using it could affect other customers' addresses.

If the provider's router looks for individual client addresses directly on the WAN, something must answer Neighbor Solicitations for them. The advanced WG/OpenVPN option therefore uses exact `/112` reservations within one allocated `/64`, together with a narrowly scoped reactive NDP proxy:

| Service | Prefix within the allocated on-link /64 |
| --- | --- |
| OpenVPN UDP | `2001:db8:100:0:100::/112` |
| OpenVPN TCP | `2001:db8:100:0:101::/112` |
| WireGuard | `2001:db8:100:0:102::/112` |

This is a specific workaround topology. It requires more specific local routes into the tunnels and NDP replies on the WAN. It is not a general replacement for provider routing. The proxy does not create client addresses or routes, or allow their traffic through the firewall.

### How the helper works

`advanced/Start-NdpProxy.ps1` and `NdpCapture.cs` are an additional implementation that requires your own pilot. Without `-Apply`, they make no changes. They capture only inbound ICMPv6 NS on a specific WAN interface, in **SNIFF + RECV_ONLY** mode. The driver copies traffic without holding it for reinjection. A separate raw socket sends the NA reply. The default `NO_INSTALL` prevents unrequested driver installation. Explicitly using `-AllowDriverInstallation` permits the standard WinDivert driver load/installation when the handle is opened. [WinDivert API and flags](https://github.com/basil00/WinDivert/blob/master/include/windivert.h).

Validation checks lengths, a direct IPv6 Next Header of ICMPv6, type 135/code 0, hop limit 255, the checksum including its pseudoheader, the router's exact source link-local address, the exact target whitelist, the permitted NS destination, and option lengths. The queue is limited to 64 entries. Replies are limited to 20/s and at most one per target/router every 500 ms. Packets with IPv6 extension headers or fragmentation are deliberately rejected. This is not a complete general-purpose NDP proxy. It also does not handle DAD from the unspecified source address. The helper assumes a trusted WAN segment; a whitelisted IPv6 source address alone does not cryptographically authenticate a router.

NAs are reactive, solicited, and sent by unicast to the trusted router. There is no periodic unsolicited loop used in place of actual NS handling. Do not disable IPv6 checksum validation or the firewall to make the helper work. [RFC 4861](https://www.rfc-editor.org/rfc/rfc4861).

### Prepare and start it explicitly

The administrator must obtain WinDivert **2.2.2-A** manually from the [official release](https://github.com/basil00/WinDivert/releases/tag/v2.2.2). This package does not redistribute its binaries. Verify the source, hash, signature of `WinDivert64.sys`, correct x64 architecture and current security requirements. Never disable driver signature enforcement or system protection to load the driver. Review the third-party contents and license separately.

Copy the required `scripts/Common.ps1` and `advanced/*` structure into a protected directory under `ProgramData\WindowsVPN`, keeping the relative paths. Allow only SYSTEM/Administrators in its ACL. Do not run the privileged helper from a directory that ordinary users can modify. In your copy of `neighbor.example.json`, replace the prefix, router, targets, binary paths and both approved SHA256 values. The example `fe80::1` is not automatically the correct upstream address.

```powershell
$root = Join-Path $env:ProgramData 'WindowsVPN\NdpPilot'
. .\scripts\Common.ps1
Protect-VpnDirectory $root
$null = New-Item -ItemType Directory -Path (Join-Path $root 'advanced'),(Join-Path $root 'scripts') -Force
Copy-Item -LiteralPath .\scripts\Common.ps1 -Destination (Join-Path $root 'scripts\Common.ps1')
Copy-Item -Path .\advanced\* -Destination (Join-Path $root 'advanced')
```

This manual preparation writes files. Run it only as part of an approved pilot. Store the edited configuration under the protected root. The template contains only seven target addresses: the server address and **one** OpenVPN client in each pool, plus three WG addresses. For a small pilot, set OpenVPN `max-clients 1`. For a larger deployment, build the whitelist from the actual client assignments and pool capacity, rather than the whole `/64`.

In this OpenVPN 2.7 arrangement, the first dynamic client IPv6 address can start at `::2`. Do not assume it starts at `::1000`; use the status file and the client's actual address as the source of truth. If the proxy covers a different range, the tunnel may work while internet replies are lost at the WAN. Check the assigned addresses and NS/NA traffic. Update the whitelist before adding a peer or changing the pool. The helper does not reload its configuration while running; stop it in a controlled way and start a new process.

```powershell
$config = Join-Path $root 'advanced\neighbor.json'
& (Join-Path $root 'advanced\Start-NdpProxy.ps1') -ConfigPath $config
& (Join-Path $root 'advanced\Start-NdpProxy.ps1') -ConfigPath $config -Apply -WhatIf
& (Join-Path $root 'advanced\Start-NdpProxy.ps1') -ConfigPath $config -RunMinutes 30 -AllowDriverInstallation -Apply
```

A first start that requires the driver is an explicit administrator choice. Later starts without `-AllowDriverInstallation` work only if the driver is already installed. With `-Apply`, the script rejects the documentation prefix. Before each start, check for an existing `stop.flag` and why it was set. To stop the helper, create that file beside it or terminate the foreground process. Sockets and the capture handle close in `finally`. Stopping the helper does not uninstall the shared WinDivert driver, and the helper does not delete the driver automatically.

Enable automatic startup only after a successful pilot, secure ACLs and neighbor resolution tests after cache expiry. The task should start a new Windows PowerShell process as SYSTEM with `-RunMinutes 0 -Apply`, without the installation switch, using `StartWhenAvailable`, restart on failure and controlled task logging. Do not assume it is ready two seconds after startup. Test a reboot and a case where WAN IPv6 is not ready on the first attempt. Automatic registration of this advanced task is not part of the default installation.

For a standard deployment, use prefixes routed by the provider. Once both IP families have been verified, continue with [MTU and performance testing](06-MTU-and-performance.md).
